## 3. 缺口清单

### P0——集成阻塞（M0 收尾前）

**G1 ABI 版本握手**【高，0.5 人日】
`PluginDef` 无版本字段。本会话已被陈旧 ABI **咬过一次**（旧头编译的 .so 静默写错成员槽位 → 拆除崩溃）——当时的对策是"文档铁律 + 同批重编"，这是人治；应产品化为机器裁决：
`PluginDef` 增 `abiVersion`（如 `CCORDIS_ABI_VERSION` 宏，改内核布局即 +1），宿主 `pluginFromLibrary` 加载即比对，不符→拒载 + 明确日志。
配套：内核自身版本号（`ccordis::version()`）进 topology。

**G2 回归测试未入库**【高，1 人日】
三份冒烟（内核 12 场景/数据面/超时）+ 容器装配冒烟全部活在 `/tmp`——**仓库内零回归保护**，任何后续内核改动都裸奔。A9-5（tst_Ccordis 接入 tests.pro + plugins/hello 入库）应立即执行；容器冒烟一并并入。CI 增加：纯净性（无 Qt 路径编译）+ ASAN + 动态往返三件套。

**G3 adapters/qt 桥缺失**【高，2 人日，M2 前置】
QString/QJson↔内核类型互转、pump 的 QTimer 官方集成、pumpHook 的 QueuedConnection 唤醒标准件、`provide<QWidget>` 非拥有注册助手——指南里全是"应然"代码，无一存在。没有它 M2 宿主接入的每一步都在重复造易错的桥。

**G4 事件风暴防护**【高，0.5 人日】
EventBus 快照分发 + 异常隔离都有了，但**没有环预算**：插件 A emit `e1`、处理器里 B emit `e2`、B 的处理器又 emit `e1`——同步总线无限递归，GUI 线程栈溢出挂死，且异常隔离救不了（不抛异常）。方案：EventBus 增**重入深度上限**（如 16）+ 每事件每轮处理预算，超限告警并丢弃。同步中间件链同理。这是控制面的最后一类未设防故障模式。

### P1——生产加固（M2/M3）

**G5 装载期安全钩子**【中，1 人日】：F7 记录在案未落地。`Context::setLoadValidator(fn(path, hash)->bool)`，策略留宿主（哈希白名单/签名）。设备产品交付前必须至少有白名单。

**G6 可观测聚合**【中，1.5 人日】：通道/超时各有 stats，但无统一出口。缺：`Context::stats()` 聚合为一份 Value（插件状态计数 + 通道统计 + 总线计数）；`plugin.failed` 事件广播（现在 lastError 只能查 topology，宿主 UI 无法主动提示）；结构化日志级别（warn/error 分级）。

**G7 配置热重载**【中，1 人日】：`Context::reload(name, newCfg)` = unload+按新配置重载（保留记录位置与依赖边）。设备调机不改代码调参数是刚需；配套"配置 schema 约定"（必填/类型/范围声明在 PluginMeta 或约定键）。

**G8 libccordis.so 构建目标**【中，0.5 人日】：当前动态插件靠宿主 exe `-rdynamic` 导出符号（开发态方案）。产品态应内核编共享库，宿主/插件共链——同时天然解决 G3 一部分链接问题。qmake + （可选）CMake 双工程。

**G9 GUI 线程亲和守护**【中，0.5 人日】：debug 构建下 `post` 之外的跨线程内核调用注入断言（记 `std::thread::id` 于根 Context，关键 API 入口比对）——把 §12 线程军规从文档变成可执行检查。

### P2——规模化（M3+/按需）

**G10 慢消费者模式选项**：邮箱只有丢旧；补 per-channel 可选"最新窗口 N 帧"与订阅者级回调耗时统计（识别谁拖慢 pump）。数据面目前 1μs/帧无压力，列为按需。

**G11 基准套件**：微基准（总线扇出/池分配/pump 吞吐）进 CI 带 regression 阈值——当前 1μs/帧是冒烟单点数据。

**G12 插件包格式**：目录布局 + manifest（依赖/版本/最小内核版本）+ 安装-升级-回滚流程。产品线插件数 <20，**从简**：目录约定 + 版本字段即可，勿造包管理器。

**G13 按插件资源计量**：Blob 池全局上限已有；按提供方计量（topology 增 per-plugin 内存/发布计数）用于现场排障，非配额执行。

**G14 崩溃隔离评估**：动态插件 segfault 带走进程，进程内无解。远期评估进程外插件宿主（gRPC/共享内存数据面）——**仅当**出现第三方闭源插件需求时立项，自研插件同仓同编无此问题。

### P3——生态（远期）

G15 doxygen API 手册 / CMake 支持；G16 脚本绑定（若需热改逻辑，先评估配置热重载 G7 是否已覆盖 90% 场景）。

## 5. 三个架构级提醒（路线纠偏，非功能项）

1. **当前最大风险不在内核，在"从未在真实宿主跑过"**。内核冒烟再绿，不等于 MainWindow 装配链路成立——M1/M2 应尽早晨接，每拖一天，"内核已验证"的置信度折旧一天。
2. **版本策略现在就要定**，晚了就是 G1 的教训在产品上重演：内核 SO 版本（SONAME）、`PluginDef.abiVersion`、插件自身版本，三层各管什么、何时 bump，写进 §7 一页纸。
3. **按实际规模设计**：本产品线插件预计 <20 个、全部同仓同工具链。OSGi 的版本协商/动态导入/服务秩 rank 等能力是百插件生态的产物——列为"永不需要"比列为"远期"更诚实，防止后人过度设计。
